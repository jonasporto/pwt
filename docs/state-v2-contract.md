# pwt state contract v2

Status: **implemented**. This document specifies the second version of
pwt's on-disk state, designed for three goals at once:

1. **A stable, versioned read contract** for external consumers (the planned
   `pwt-ui` dashboard, statuslines, scripts) that watch pwt state instead of
   invoking the CLI.
2. **Removing `jq` as a runtime dependency.** Today pwt has ~130 `jq` call
   sites; most are single-field reads of small JSON files. v2 state is
   parseable and writable in pure bash.
3. **Startup performance.** The measured ~250ms startup is dominated by
   dozens of `jq` process spawns; v2 turns those into file reads and string
   splits.

JSON does not disappear: it remains the **output** format (`list
--porcelain`, `info --porcelain`, `gateway status --json`, and the new
`pwt state --json`), generated by a small pure-bash `json_escape` helper.
What changes is the **internal storage** format.

## Layout

```
~/.pwt/
  state-version              # single line: "2"
  events.log                 # append-only activity feed (TSV)
  config                     # global settings, dotted keys (was config.json)
  claude-statusline          # statusline settings (was claude-statusline.json)
  projects/<name>/config     # key=value (was config.json)
  projects/<name>/gateway.state     # gateway daemon state (was gateway.json)
  state/<project>/<worktree>.meta   # key=value, one file per worktree
                                    # (replaces the monolithic meta.json)
  jobs/<id>.job              # key=value (was <id>.json)
  jobs/<id>.log              # unchanged
  trash/<name>.trash         # removed-worktree records (was <name>.json)
  trash/<name>.patch         # unchanged
  cache/                     # unchanged (already text/TSV, regenerable)
```

Every file above is part of the contract: it is what pwt reads and what
migration produces. Consumers normally care about `state-version`,
`state/`, `jobs/`, `projects/*/config` and `events.log`; the rest is listed
so nothing under `$PWT_DIR` is a surprise.

### File format: flat key=value

One `key=value` per line. Keys match `[A-Za-z0-9_.-]+` (uppercase and `-`
appear in tool names such as `ai.tools.gpt-4o`) and are rejected otherwise, so
a key can never contain the `=` that would make pwt and a consumer disagree
about where the value starts. Nested concepts flatten with dots
(`editor.default=vim`, `ai.tools.claude=claude --resume`).

Values are raw except backslash, newline, tab and CR, escaped as `\\`, `\n`,
`\t` and `\r`. Only newline can break a `key=value` line; tab and CR are
escaped because the same escaper writes `events.log`, which is tab-separated.
`_state_escape` and `_state_unescape` must be edited together: every sequence
one emits, the other must reverse. Read in bash with
`while IFS='=' read -r k v` (split on first `=` only); written with
`printf '%s=%s\n'`. Unknown keys MUST be preserved by writers (user-defined
metadata like `phase`, `next`, `blocked` lives beside built-ins).

### Per-worktree meta files

`meta.json`'s nesting (`project → worktree → fields`) becomes one file per
worktree: `state/<project>/<worktree>.meta`. Rationale:

- **Watchability**: a consumer (pwt-ui) gets per-worktree fsnotify events and
  reads only what changed, instead of re-parsing one growing JSON blob.
- **Crash/conflict safety**: `meta set` rewrites one small file atomically
  (`tmp + mv`), never the whole database.
- **The board model**: one-file-per-card is the proven shape for
  agent-driven kanban (cf. Backlog.md); pwt's phase board reads directly.

Example `state/myproject/TICKET-123.meta`:

```
branch=user/TICKET-123
path=/home/me/worktrees/TICKET-123
port=5024
base=main
base_commit=abc1234
created_at=2026-08-07T12:00:00Z
description=fix login flow
phase=review
next=address PR comments
```

### Job records

`jobs/<id>.json` fields are already flat; `<id>.job` carries the same keys
(`id`, `pid`, `pgid`, `command`, `worktree`, `project`, `log`, `started_at`,
`status`) in key=value form.

### Events log (`events.log`)

Append-only TSV, one event per line, written by pwt commands at the moment
they mutate state:

```
<iso8601-ts>\t<project>\t<worktree>\t<kind>\t<detail>
```

Kinds (initial set): `create`, `remove`, `server_start`, `server_stop`,
`job_start`, `job_end`, `meta_change` (detail: `phase=review`), `adopt`,
`restore`. Writers append with a single `printf >> ` (atomic for lines under
PIPE_BUF); readers tail it. This single file is what makes an activity feed
and "notify me when it finishes" trivial for consumers. Rotation: pwt
truncates to the last N=1000 lines opportunistically on startup-adjacent
commands (never mid-append).

## The read contract for consumers

- `~/.pwt/state-version` declares the schema. Consumers MUST check it and
  refuse-or-degrade on unknown versions. Any breaking change to file
  locations, formats, or key semantics bumps it.
- Built-in keys above are stable; new keys may appear at any time (consumers
  ignore unknown keys). User-defined meta keys are free-form.
- `status` in job records is advisory (may be stale if a process died);
  consumers wanting truth check the pid themselves — same as pwt does.
- Aggregated snapshot: `pwt state --json` emits everything (projects,
  worktrees+meta, jobs) in one versioned JSON document for consumers that
  prefer shelling out once over reading files.

## Migration

- On first run, if `state-version` is absent and legacy JSON exists, pwt
  migrates automatically: legacy files are converted, then renamed to
  `*.v1.bak` (kept until the user removes them; `pwt doctor` reports them).
- Migration is the **only** code path that still reads legacy JSON. It uses
  `jq` if installed (every legacy install has it, since it was previously
  required); otherwise it instructs the user to install jq once or start
  fresh. Fresh installs never touch jq.
- `jq` leaves `doctor` required-tools; the dependency list shrinks to
  bash ≥ 3.2 + git + coreutils.

## jq call-site disposition (inventory 2026-08-07: ~132 sites)

| Category | ~Sites | Disposition |
|---|---|---|
| Single-field reads of config/meta/jobs (`jq -r '.x // empty'`) | ~90 | `state_get <file> <key>` pure-bash helper |
| Field writes (`jq '.x = $v' > tmp && mv`) | ~20 | `state_set <file> <key> <value>` (rewrite file, preserve unknown keys) |
| JSON generation (`jq -n` for porcelain/job records) | ~12 | `json_escape` printf helper for output; key=value for records |
| Batch project index build | ~6 | already TSV-cached; build from key=value directly |
| Misc (`jq .` pretty-print, version probe) | ~4 | drop or gate behind "if jq available" |

## Non-goals

- No SQLite, no daemon: files stay human-readable, greppable, and diffable;
  the consumer layer (pwt-ui) adds liveness via fsnotify, not pwt.
- No change to porcelain output shapes in this step (JSON out stays as-is,
  so existing agent workflows keep working unchanged).

## Concurrency

`state_set` is read-modify-write on a single file, with no lock. Because each
worktree, job and project owns its own file, concurrent writes to *different*
records cannot interfere — an improvement over v1, where every metadata write
serialized through one `meta.json`.

Two writers racing on the **same** record can still lose a key: both read the
file, both rewrite it, the later write wins. In practice writers to one record
are the same worktree's own commands, so this is rare; if you script parallel
`pwt meta set` calls against one worktree, serialize them yourself.

Readers never see a partial file: writes go to a temporary file and are moved
into place atomically.
